## Operating Contract

### User authority and scope

- The user's latest explicit instruction controls project intent, scope, priorities, and trade-offs.
- Analysis, review, research, and planning are read-only unless the user asks for file changes.
- Work only in requested paths; unrelated dirty files are not a reason to rewrite or clean them.

### Deletion and destructive actions

- Never delete, move, rename, empty, or replace a maintained file without written permission naming the affected path.
- Before an irreversible Git/filesystem action: show the exact command, cwd, branch/HEAD, affected paths, current status, expected effect, and rollback limits; obtain two immediate written confirmations separated by a refreshed preflight; then audit the exact execution.
- Prefer inspection, a new non-destructive copy, or targeted edits. Never use broad cleanup, reset, restore, stash, or overwrite commands on concurrent work.

### Git and external effects

- Do not branch, create a worktree, commit, merge, rebase, push, deploy, publish, or change dependencies without explicit approval for that action.
- Implementation approval is not commit or deployment approval. Stage only reviewed owned paths when staging is separately authorized.
- Do not install packages merely because `node_modules/` is absent; request approval for the exact package-manager command.

### Editing and concurrency

- Read the current file and nearby contracts before editing; record relevant path status and inspect each meaningful diff immediately.
- If another process changes an owned path during an edit, stop and preserve both versions rather than choosing silently.
- Prefer bounded manual edits. Add a file only for a distinct required responsibility or an explicit request.
- Identify authoritative generators before touching generated output; edit the source, run the canonical generator deliberately, and review source/output together.

## Astro Application Rules

- Use pages for routes, layouts for shared documents, components for cohesive markup, and content collections for validated content.
- Render semantic HTML first. Hydrate only the smallest browser-owned interactive state, with the least eager compatible directive.
- Complete content, primary navigation, source boundaries, and core discovery must remain understandable without JavaScript.
- Use native controls, visible focus, responsive composition, readable measure, explicit tokens, and `prefers-reduced-motion` fallbacks.
- Treat accessibility, metadata, performance, loading, empty, and controlled-failure states as acceptance behavior—not post-build cleanup.
- Preserve target conventions instead of importing an example's framework, folder tree, or dependency set.

## Route and Publishing Invariants

- HTML routes use canonical trailing slashes; file endpoints (`404.html`, `robots.txt`, `sitemap.xml`) do not.
- Reuse hub, entry, and taxonomy patterns; avoid duplicate canonical content and thin tag/facet/tool pages.
- Keep case studies under `/case-studies/[slug]/`; promotion must not change their canonical paths.
- One visibility policy drives routes and discovery: `draft` produces no route; `noindex` remains crawlable but is excluded from discovery; `public` may appear in discovery.
- Sitemap exclusion is explicit. Structured data must match visible content.
- Ordinary SEO fundamentals come first; never promise indexing, ranking, rich results, or AI citation.
- Claims, metrics, testimonials, logos, dates, freshness, and public evidence require substantiation and permission.
- Never commit raw analytics, contracts, customer data, credentials, private approvals, or unrestricted model content.
- Crawler policy is not an authorization or privacy boundary; distinguish search/retrieval access from model-training access.

## Commands and Verification

Declared scripts:

```bash
npm run dev
npm run check
npm test
npm run build
npm run preview
npm run verify
```

The default integrated gate is:

```bash
npm run check && npm run build && npm test && npm run verify
```

Build precedes tests: several suites read `dist/` at import time, so running
them first asserts against the previous build instead of the current one.

Before claiming completion:

1. run the narrowest relevant check, then the integrated gate when warranted;
2. inspect every owned diff and run `git diff --check -- <owned-paths>`;
3. report command exit statuses and observed results, not expectations;
4. report the absolute checkout, branch, HEAD, and final status;
5. list blocked checks and remaining risks;
6. confirm no file was deleted and no unrelated/runtime work was altered.
